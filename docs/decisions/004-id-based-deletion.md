# ADR 004: Implement Surrogate ID-Based Memory Deletion

- **Status:** Accepted
- **Date:** 2026-03-19
- **Author:** Victoria Cheng

## Context and Problem Statement

The system utilizes an established **"Retrieve -> Confirm -> Act"** safety protocol for all destructive operations. However, the initial implementation of the `delete_memory` tool relied on natural keys (`content`, `context_key`) during the final execution stage. This introduced a significant data integrity risk:

- **Content Collisions**: If multiple records shared the same content (e.g., identical instructions across different project contexts), a content-based deletion would purge all matching entries simultaneously, even if the user only intended to delete one.
- **Matching Fragility**: Minor variations in whitespace or hidden characters could cause targeting to fail, or worse, target the wrong record if two entries were visually similar but technically different.
- **Workflow Ambiguity**: While the "Confirm" stage presented a specific memory, the content-based "Act" stage could not technically guarantee that only the confirmed record was removed.

## Decision Outcome

We transitioned the final execution stage of the `delete_memory` workflow to use unique surrogate `id`s generated by the SQLite engine. This refinement leverages the existing safety protocol to ensure surgical precision:

1. **Discovery**: The agent uses search tools to identify the target memory and retrieve its unique `id`.
2. **Double Confirmation (Existing)**: The specific memory is presented to the user for explicit confirmation.
3. **Deterministic Execution (New)**: The `delete_memory` tool now executes the removal using the immutable surrogate `id`, guaranteeing that one `id` corresponds to exactly one record.

## Consequences

### Positive

- **Operational Safety**: Eliminates the risk of "mass-deletion" caused by content collisions, ensuring that destructive actions are strictly scoped to a single record.
- **Deterministic Precision**: Provides a guaranteed one-to-one mapping between the user's confirmed intent and the final database state.
- **Hardened Governance**: Strengthens the existing safety protocol by replacing fragile string-matching with immutable primary key targeting.

### Negative

- **Client Tracking**: Requires the MCP client to track and provide the surrogate `id` for the final deletion call.

## Verification

- [x] **Automated Tests**: Updated `internal/service/memory_test.go` and `internal/mcp/tools_test.go` to validate ID-based deletion logic and error handling.
- [x] **Performance**: Confirmed sub-millisecond latency for ID-based lookups ($O(1)$) via the project benchmark suite.
